# AR統合アプリ 企画メモ

作成: 2026-09-12
前提: `E:\claude_projects\ar` の試作（マーカー型・床置き型・マーカー生成・usdz変換・印刷PDF・診断ページ）は完成し、
https://gearbox00.github.io/ar/ で公開済み。本メモは、その上に「サービスとして売れる形」を組む企画。

## 1. 調べたこと（2026-09-01〜09-12）

### 市場の動き

1. 8th Wall（WebAR最大手）が終了。2026-02-28に編集停止、2027-02-28にホスティング終了
2. palanAR が STYLY に統合（2026-05-19名称変更、アプリ版は2026-08-05終了）
3. 国内SaaSの料金: STYLY WebAR 無料(3件)／月額¥38,500(10件)、Pitat-AR 無料〜月額¥7,980
4. 制作会社の相場: フォトフレーム20〜80万円、スタンプラリー20〜300万円、オリジナル開発100〜500万円

→ 基盤サービスを作る場面ではない。**制作＋自社ホスティングで、月額¥38,500の中身を安く出す**のが立ち位置。

### 効果が数字で示されている用途

| 用途 | 数字 | 出典 |
| --- | --- | --- |
| 家具・什器の原寸配置 | 返品 −25〜48%（Wayfair −43%、Macy's 5〜7%→2%未満） | orbe3d, framesixty |
| 同上 | 転換率 Wayfair +92%、IKEA Place +189%、Houzz 11倍 | framesixty, bigcommerce |
| 購買前の安心感 | 80%が「自信が持てた」、66%が「返品しにくくなった」 | brandxr 2025 |
| ARフォトフレーム | SNSへの投稿（UGC）が起点。ジョーカー映画でTwitterに画像が溢れた | balance.bz |
| ARスタンプラリー | 回遊・来店・滞在時間増（くまモンテクテク） | coco-ar, less-ar |

※ 数字は海外の大手小売のもの。中小での再現性は未確認。

### マネタイズの型

| 型 | 向き不向き |
| --- | --- |
| 広告モデル | **不可**。月間100万DAUが目安（bakusoku-seisaku） |
| B2Cアプリのサブスク | ARだけでは継続理由が弱い。イベントが終われば止まる |
| **B2B: 初期制作費 + 月額（ホスティング・計測）** | **これが本命**。相場の月額¥38,500が比較対象 |
| B2B: キャンペーン単位の請負 | 単発。印刷会社・デザイン事務所経由で反復させる |
| 既存SaaS（スタンプカード等）への付加機能 | 解約理由にならず差別化になる |

## 2. 盛り込む機能（有効と判断したもの）

### 実装済み（試作で完成）

1. 印刷物にかざすとCGが出る（マーカー型、指で操作可）
2. 床に原寸で置く（glb/usdz、iOS/Android対応）
3. マーカー生成・認識データ変換・印刷PDF・モデル変換・診断ページ

### 追加する

| # | 機能 | なぜ有効か | 難しさ |
| --- | --- | --- | --- |
| 4 | **ARフォトフレーム／撮影** | SNS投稿で拡散する。効果が最も見えやすい | 低〜中 |
| 5 | **ARスタンプラリー（マーカー/QR巡回型）** | 回遊・来店に直結。GPS型より確実に動く | 中 |
| 6 | **計測** | 閲覧・認識・撮影・達成の回数。**これが無いと客に効果を示せず、月額が取れない** | 中 |
| 7 | **管理画面** | クライアントが自分でマーカー・中身・スポットを登録。これで「制作」から「サービス」になる | 高 |
| 8 | 商品カタログ型の床置き（複数モデルの切替） | EC・什器の用途。数字が最も強い | 低 |

### 入れない

| 機能 | 理由 |
| --- | --- |
| 顔認識の試着（メイク・メガネ） | 精度と端末差が大きく、iOSの制約もある。別製品として扱う |
| GPS型スタンプラリー | 屋内・都市部で位置がぶれる。マーカー/QR型で代替できる |
| 現場図面の重ね合わせ | 用途が違う（業務系）。求められたら別途 |
| ゲーム性の高い仕掛け | 制作費が跳ね、効果の測定も難しい |

## 3. 決めないと進めない事項（ユーザーへの確認）

1. **誰が使うか**: 自社の営業デモとして使う／クライアントが自分で登録できるサービスにする
   → 後者なら管理画面とデータベースが要る。作りが大きく変わる
2. **データの置き場所**: 計測と管理画面を入れるならDBが要る。Firebase／Supabase／Xサーバー(PHP+SQLite)のどれか
   → 既存の自社SaaS（stamp_card 等）と技術構成を揃えるのが保守上は楽
3. **最初の業種**: 印刷会社経由（チラシ・パッケージ）／小売・EC（什器・商品）／観光・イベント（スタンプラリー）
   → 最初の1件に合わせて機能の優先順を決める

## 4. 段階案

| 段階 | 内容 | 成果 |
| --- | --- | --- |
| 1 | フォトフレーム＋撮影・保存・共有、商品切替 | デモが「見せる」から「持ち帰れる」になる |
| 2 | 計測（静的ホスティングでも取れる形） | 効果の数字が出せる |
| 3 | スタンプラリー | 回遊系の案件を取れる |
| 4 | 管理画面 | クライアントが自走。月額の根拠になる |

段階1〜2は既存の静的構成のまま作れる。段階3から保存先、段階4からDBと認証が要る。
